# Publish subagent progress on `pi:background-tasks`, and treat its v1 fields as frozen

`packages/subagent` publishes a snapshot of its live runs on the event channel `pi:background-tasks`, and answers a `pi:background-tasks:request` with the current one. The payload is `{ version: 1, source: "pi-archimedes", sessionId, tasks[] }`, each task carrying a stable `<toolCallId>:<index>` id, a `label`, `detail`, partial `usage`, and the optional `name` / `task` / `transcript` extensions (#171).

Until now every channel this suite emitted was internal. The six in `core/src/events.ts` are `archimedes:`-prefixed and both ends live in this repo — the bridge maps several onto Client push frames, and a rename is a wire change we make in one commit across both sides. `pi:background-tasks` is the first contract with a consumer we do not own. It is also not a contract we wrote: `pi-subagents` published it and Slate consumed it before this package emitted anything, and we joined as a second publisher. That is what changes the status of the field names. A field in an internal event is a refactoring target; a field another repo's code reads is a versioned surface, and the only way to change it is to add to it. The three optional extensions are ours, and Slate's PR is written to read them, so this ADR pins them now rather than after the first release ships — at which point the option to rename is gone.

**The namespace.** `pi:` is not a namespace any of us owns, and it is worth being precise about what the host actually reserves, because the honest answer is "less than one might assume". pi 1.4.0 ships `createEventBus()` and hands the same bus to every extension of a session, and it emits **nothing** on it itself: grepping the shipped `dist` for host-side `events.emit` call sites finds none, and the one `pi:`-prefixed string in the whole package (`pi:image-resize-response`, `utils/image-resize-core.js`) is a `worker_threads` message type on a different transport, not a bus channel. So the host defines no bus vocabulary at all, does not validate channel names, and does not deliver events across processes. Under that prefix, `pi:background-tasks` is a convention the ecosystem settled on without us, and we joined it as the second publisher rather than defining it.

We publish under it anyway, because the alternative is worse. `archimedes:background-tasks` scopes the channel to *this suite*, which is wrong in a specific and confusing way — a second publisher with a different implementation would have to either impersonate us or invent a third name, and a consumer wanting "whatever background work is running" would have to subscribe to each vendor's channel separately. The value of the channel is that it names the *concept*, so any publisher and any dashboard meet on it. The `source` field is what carries provenance, and it is mandatory and bounded for exactly that reason: Slate keys rows by `source` + task id, so two publishers using the same task id stay separate rows. The risk we accept is that an unowned prefix can be claimed later by someone with more authority than us. The one that matters is pi itself: if a host release ships its own background-task protocol on the bus, we adopt pi's, because a host-defined contract beats a convention by definition. That is a version bump and a rename of `BACKGROUND_TASKS_CHANNEL`, not a redesign — which is why the channel strings, like the six `archimedes:` ones in `core/src/events.ts`, live in one module.

**Considered Options**

- **`archimedes:background-tasks`, our own prefix** — rejected: it reads as "Archimedes' private bus" and forecloses the multi-publisher shelf that is the entire point. The suite name does not own the concept of a background task, and the objection is no longer hypothetical — `pi-subagents` is already publishing on `pi:background-tasks` with a different implementation, so our prefix would have put two publishers of the same idea on two channels and left every dashboard to subscribe to both.
- **Let the dashboard read the subagent's own tool events** — rejected: the consumer's own PR states the boundary as its reason for existing ("show live status without parsing another extension's tool events, reading native sessions, or gaining worker control"), and states it back at us in its docs. Parsing another extension's tool renderer output couples a consumer to our presentation internals; ADR 0029 moved presentation onto renderers for the opposite reason, so those events are explicitly *not* a contract.
- **A host request for a first-class background-task API** — rejected for now, not forever: the protocol here is small, display-only, and already works across two repos. If it earns a place in the host, the migration path is the namespace note above.
- **Publish richer state — outcomes, history, run controls** — rejected: see authority below.

**Additive-only from here.** The v1 field set is closed for modification. Renaming `label`, retyping `startedAt`, changing `kind`, or changing what `usagePartial` means are all breaking changes that require a `version: 2` and a period of publishing both. Adding a field is free, and every consumer must treat an unknown field as ignorable — which is how `name`, `task` and `transcript` shipped in the first place, and why `label` and `detail` stay populated even though `name` + `task` now carry the same information better. The optional-ness of the three extensions is load-bearing in the other direction too: `pi-subagents` publishes v1 with none of them (`pi-subagents/src/dashboard.ts` builds `id`/`label`/`kind`/`state`/`startedAt`/`usage`/`detail` and nothing else), and Slate reports tested support for that row. A publisher that assumes its own extensions are present will pass its own tests and fail in someone else's dashboard. `state` is deliberately absent from the list above, because it is not a closed set — see below.

**State is an open vocabulary, not a union.** Our rows carry `starting` or `running` and nothing else. `pi-subagents` — which shipped this channel before us, and whose `pi-subagents/src/dashboard.ts` is the other half of what v1 *is* — maps its own eight-state machine onto the same field and publishes `waiting`, `cancelling` and `cleanup_unknown` as well. Neither list is wrong; the field is a display label that a publisher derives from its own lifecycle, and v1 never enumerated it. So a consumer must treat `state` as an opaque string with a fallback rendering, and no publisher may assume its own values are the whole domain. We keep ours closed for a reason, though: the moment we emit a third value we have invented an outcome, which authority below forbids.

**Settled work leaves the shelf — and that is the one rule both publishers already agree on.** Ours removes a task on completion, failure, cancellation, replacement, reload and shutdown; theirs filters `completed`/`cancelled`/`failed` out and says so in its own comment ("Settled runs remain accounting evidence, not display occupancy"). Slate relies on it in both directions: it clears a publisher's rows on an empty snapshot, and it states "Slate adds no outcome or control semantics". That agreement is the load-bearing part of v1, and it is the rule a future change must not quietly break: a row that lingers after its run is over is a row someone will act on.

**The other publisher is also a reminder about trust.** `pi-subagents` puts `pid`, a `totals` block and a native session id in its rows, and its `detail` is a multi-line string containing the child's native session id and the text `Inspect/control using /subagents <id>`. Our bounds are single-line by construction. Both are legitimate, because a consumer renders what it is given and none of it is ours to validate: a consumer must treat every field on this channel as untrusted display text from an in-process peer, never as a control surface or as evidence about a run. This is also the honest limit of what v1 fixes — it is a *display* rendezvous, not a schema, and there is no validator that both publishers pass beyond the field names a consumer reads.

**Authority, and the one thing the protocol must never grow.** The publisher is authoritative and the snapshot is a *projection*, not a record. Only live runs appear — `starting`, then `running`, then gone; the protocol deliberately invents no `idle`, no history and no outcome, because the moment a dashboard renders a terminal state it becomes a second source of truth for whether a run succeeded, and Archimedes' tool row is that source. The same reasoning forbids run controls: no cancel, no input, no restart rides on this channel, and a consumer must not gain authority over a child process by subscribing to a display feed. A consumer that wants the authoritative result reads the tool result. This is a constraint on us as much as on them — the tempting follow-ups ("just add a cancel id", "just keep the last finished row") are the ones this paragraph refuses.

**`transcript` carries reasoning, and we say so in the docs.** The progress stream mixes thinking parts into `accumulatedOutput` as `[thinking] …` (`handlers.ts`), which reaches `progress.output` and from there the transcript. So the field ships up to 64 KiB per task of the run's reasoning, not only its answers, and `packages/subagent/README.md` and `docs/features/subagent.md` both say so in those words. This is not a leak: an expanded Archimedes subagent row already renders the same string, so nothing reaches the field that a user could not see by expanding the row. What changes is the *shape* of the exposure — bulk, machine-readable, to every extension in the session, rather than to a human reading their own terminal. A publisher that hides this gets to keep the surprise when someone builds a dashboard that logs it. Alongside it, the publisher's other guarantees stay as advertised: terminal controls are stripped, every bound is a documented character count, and the row is assembled from public progress strings rather than by copying host objects.

**Consequences**

- **The published row is handed out by reference, so it is frozen.** `pi.events` passes the emitted object to each listener without copying, and the snapshot memo returns the *same* object across heartbeats. A consumer that normalises a field in place — `row.transcript = row.transcript.trim()` is an ordinary thing to write — would poison the memo for the rest of the run, silently and permanently. `toBackgroundTask()` now `Object.freeze`s the row and its nested `usage` (freeze is shallow, and `usage` is the one nested object), which turns that consumer bug into a loud throw in the consumer instead of a corrupted publisher. The 2 MiB budget loop is unaffected: it copies with `{ ...task }` before mutating, and a spread of a frozen object is unfrozen.
- **The freeze is a promise to consumers we cannot see**, which is the point of it. A future field that must be mutable in place means either a copy per snapshot or a broken promise; copy per snapshot is the answer, and it is cheap next to the sanitizer the same call already runs.
- **Two publishers on one channel is now a supported configuration**, and a third-party publisher can appear without our knowledge. Every bound in `background-tasks.ts` is therefore a bound on *our* publishing only; a consumer must bound what it accepts independently, and Slate does (publishers, rows per publisher, combined rows, per-task and aggregate transcript character budgets). Nothing here protects a consumer from a hostile publisher, and no consumer should read a transcript as trusted content.
- **Session scoping is part of the contract, not an implementation detail.** A snapshot names one session, the request handler answers only for a matching session id, and a foreign in-process session's lifecycle events are ignored — a subordinate in-process session must not clear the live session's shelf (the failure class of #156, and the reason this state is held in the `register()` closure per AGENTS.md rather than at module scope).
- **`pi-latest` does not cover this protocol.** The bump rehearsal type-checks and unit-tests against the newest pi train, and would not notice a host that later defines `pi:background-tasks` itself, because nothing here breaks — the two would simply coexist on one name. The trigger to revisit is a host release note or a type declaration, not a red build.
- The consumer's independence is what makes the ordering question moot: neither #171 nor the Slate PR blocks the other, and this repo merges first because the publisher is the authoritative side of the contract.
