# Per-session state (`#156`)

## The rule

**Per-session state lives in the `register()` closure. Never at module scope.**

Pi caches an extension **module** per process — the loader's cache is keyed by extension path, so a cache hit skips the import and module-scope bindings survive a session switch — and then re-invokes the cached factory with a **fresh `pi`** for every session. The factory closure is therefore per-session for free; anything hoisted above it belongs to the process.

The failure that makes this a bug rather than a style preference: a subordinate **in-process** session — a third-party subagent child, bound with no `uiContext` — runs its `session_shutdown` against the same module instance the live parent session is using. Any module-scope binding that handler can write or clear is the live session's, and clearing it is silent. That is #156: `image-paste` lost its queue (the paste key returned before reading the clipboard), `ui` lost the border spinner's interval and its hand-back flag, and `meta`'s shutdown ref was liveness-gated but not owner-gated. All three shipped, and no test could see it — `packages/subagent`, the suite's own subagent package, **forks a separate process**, so a different module instance and no repro.

`ask` (`packages/ask/src/index.ts:7-8`), `todo` (`:14-17`), `session-name` (`:287-288`) and `footer` (`:39`) already kept their state inside `register()`; the three broken packages hoisted it. Pi's own `docs/extensions.md` §State Management prescribes the closure, states plainly that module-level variables stay shared across sessions, and requires teardown handlers to be idempotent.

## What is not a session key

- **`ctx` is not an identity.** pi builds a **fresh `ExtensionContext` per `emit()`**, not per session, so a `WeakMap` keyed on `ctx` gains an entry per event and never finds the session's. It is the tempting fix and it cannot work.
- **`ctx.hasUI` is not a session guard.** It is `uiContext !== noOpUIContext` — it answers *"is there a dialog-capable UI attached?"* — and it is **`true` in RPC mode**, and for any host-supplied UI shim. It appeared to work for #156 only because the child in the triggering package binds with no `uiContext`. Never use it to decide ownership; use `ctx.mode === "tui"` when the question is really "is this interactive".
- **`ctx.sessionManager.getSessionId()` is the identity** when one is needed: a `uuidv7`, stable within a session, distinct across `/new`/`/fork`, and — unlike `getSessionFile()` — always defined. Read it at handler time. The `session_shutdown` **event payload** carries no such field (`type`, `reason`, `targetSessionFile?` only), and `reason: "quit"` is ambiguous between a real quit and a child teardown, so a guard on the event cannot tell whose shutdown it is.

There is **no sanctioned per-session store** on `pi` or `ctx` (pi's only persistence is `pi.appendEntry()`, durable and session-scoped, and `pi.events`, a process-wide bus). Upstream tracks the gap in Discussion #1546 and has not closed it.

## The shapes that are correct

1. **Closure state, per registration** — the default. `registerImagePaste(pi)` creates `ctxRef`/`queue`/`pasting` inside itself and hands back an `ImagePasteSession` handle (`initSession(ctx)` / `shutdown()`), so whoever holds the handle can only reach the session that created it. Same for `packages/ui`, whose `uiRef`/`uiCtx`/`spinFlag`/`spinInterval`/`styledTools` live in `registerUI`'s closure.
2. **A session-keyed `const Map` at module scope** — `meta` only, and for a specific reason. meta registers image-paste from inside `session_start` (heavy deps stay lazy) but must tear it down from a **top-level** `session_shutdown` handler, because registering `session_shutdown` inside `session_start` accumulates handlers on every `/reload` (AGENTS.md's event-handler rule). A top-level handler cannot see a per-session closure, so `meta/src/index.ts` keeps `const imagePasteSessions = new Map<string, ImagePasteSession>()` and keys it with `sessionKey(ctx)` = `ctx.sessionManager.getSessionId()`. **Ownership is the key, not the liveness of a stored ref**: the shutdown handler looks up its own session's entry, calls `shutdown()` on it and `delete`s it — a session that registered nothing finds nothing, and a foreign session cannot reach another's entry. A `const` Map whose *contents* change is not the bug shape: the binding is never assigned, so no handler can repoint it at another session's state.
3. **Teardown that is idempotent and hands back only what it took** — see ADR 0031; `ui`'s `session_shutdown` restores the working row only `if (spinFlag)` and calls `stopStartupListing()` only when `weInstalledTheSplash` says this registration put the header there.

## What the guard checks, and where it is blind

`packages/core/src/session-state-discipline.test.ts` walks every `packages/<name>/src` and `meta/src` (the same walk as `log-discipline.test.ts` and `screen-mode-discipline.test.ts`) and flags a module-scope `let`/`var` whose **binding is assigned** from a session lifecycle path. Three hops: inside a `pi.on("session_start" | "session_shutdown" | "session_before_switch" | "turn_start")` handler body; **or inside a function that handler body calls directly, in the same file**; **or in another file, inside the body of a function the handler body calls through a named import** — one module boundary, with `as` aliases honoured and `import { x } from "./barrel.js"` chains followed to the file that declares `x` (bounded, so a re-export cycle cannot hang the run), then transitive inside that target file. The cross-module hit is reported against the **target file and the target's declaration line**, so an allow-list entry still pins `file` + the exact trimmed declaration. Hop 2 is mandatory, not thoroughness: #156's assignment was `_queue = null` inside a named teardown function one call away from the handler, so a one-hop rule reads green over the bug that shipped. Hop 3 exists because the same blind spot shipped `packages/diff`'s config holders (below). Mutating a binding's *contents* (`map.set()`, `arr.length = 0`, `obj.field = …`) is not an assignment to the binding, which is what makes shape 2 above a real escape rather than a collector artifact — the liveness test pins a **`let`** Map mutated through `.set()`/`.delete()` precisely because a `const` Map would pass without proving anything about the assignment test.

Four bindings are allow-listed today, on two cards: `notify`'s `notifyTimer`/`pendingTrigger` (`packages/notify/src/index.ts:197`, `:198` — a foreign shutdown cancels the live session's pending delayed notification; minor, deferred, `tsk_9a0926e5-2d94-43bd-941a-ccf9ffe06bd7`) and `ui`'s `frameTimer`/`revealTimer` (`packages/ui/src/startup/index.ts:171`, `:172` — cleared by `stopStartupListing()`, reached from `packages/ui/src/index.ts:183`'s `session_shutdown` one module away and gated by `weInstalledTheSplash`, so worst case a cut-short splash reveal; deferred, `tsk_00a5ad67-8bc1-42e4-b999-d75196ec37c2`). The `ui` pair is new to the list because the guard can now **see** it: it used to be excused by the rule's shape, and the file pins that flip (`EXCUSED` counts exactly two hits there). Nothing in `packages/diff` needs an entry.

**The guard is a blind spot, not coverage.** Two walls survive the new hop, and both are named with the site they hide:

- **Namespace imports are not followed.** The guard's call matcher only sees a plain `name(` — it cannot match `events.onSessionStart(ctx)`, and `import * as events` hands the resolver no symbol to look up, so `core/src/bridge/index.ts:160`'s `session_start` handler still cannot be seen writing `bridge/events.ts:38`'s `sessionCtx`. Widening the wall would not be free either: the same handler calls `channel.configure({ active, socketPath })` at `core/src/bridge/index.ts:162` through `import * as channel`, so `bridge/channel.ts:66-67` would be flagged too — honest one-socket-per-process state, with no exemption category to put it in. The `NAMESPACE_IMPORT_NOT_FOLLOWED` fixture in the guard file pins the wall, so widening it is a deliberate edit rather than an accident.
- **Dynamic `import()` is not followed.** `meta/src/index.ts:162` reaches `@pi-archimedes/diff` from its own `session_start`; whatever that module holds at module scope is invisible to the guard, in either direction.

Two older walls stand too:

- An assignment inside a closure a handler **passes elsewhere** is not followed, because the callback is not a `pi.on` handler body: image-paste's paste handler `pasteFromClipboard` (`packages/image-paste/src/index.ts:223`, handed to `pi.registerShortcut()` at `:240`) is the case that mattered — pre-fix it assigned the module-scope paste mutex, and the guard cannot reach an assignment made there however it is written. The cross-module hop respects this wall too: it collects the handler body's call surface with nested closures blanked, so a call made inside `ctx.ui.setFooter((…) => { render() { … } })` never starts one.
- The assignment test is `name = …` — compound and logical assignment (`count += 1`, `cache ||= …`) is not matched, and neither is a handler registered through anything other than a literal `pi.on("…")` call.

`bridge/events.ts` needs no entry and stays invisible by the rule's shape, which the guard asserts rather than assumes. The process-wide state the guard deliberately leaves alone — footer's git/jj/token-stat caches, `bridge/channel.ts`, `ui/src/thinking/theme.ts` — is out of scope for structural reasons that are each specific: the footer caches are written from a `render()` callback the handler hands to `ctx.ui.setFooter()`, which the closure wall above does not follow; `ui/src/thinking/theme.ts`'s `piThemeReady` from a first-use probe on a render path; and `bridge/channel.ts`'s `active`/`socketPath` by `configure()` at `bridge/index.ts:162`, which the handler reaches through `import * as channel` — the namespace-import wall again — with values the handler derives from the environment plus `ctx.mode`, not from session state. `packages/diff`'s `shiki.ts`, `render/shared.ts` and `ansi/codes.ts` no longer belong on that list at all, because they no longer hold anything for the guard to ignore: `render/shared.ts` and `ansi/codes.ts` declare no module-scope `let`/`var` whatsoever, and `shiki.ts` declares only `_shikiReady`, a run-once warm-up flag its own `ensureShiki()` sets. `packages/diff` now carries exactly two module-scope bindings, `_TextComponent` and `_shikiReady`, and `packages/diff/src/module-state.test.ts` pins that shape (including the ban on an exported `setConfigGetter`) so it cannot regress by moving an assignment to another file.

### The leak this card closed (`packages/diff`, #163 — past tense: the code is gone)

`diff/src/shiki.ts` and `diff/src/render/shared.ts` each held one process-wide `let _getConfig`, and `registerDiffTools` repointed both through a `setConfigGetter` — so two sessions in one process shared one config slot, because pi caches the extension module per process. Reproduced against the real modules before the fix: two `registerDiffTools` calls with different readers, then render as session A — what A's row read went from `{"diffTheme":"github-light","diffSplitMinWidth":100,"split":true}` to `{"diffTheme":"dracula","diffSplitMinWidth":400,"split":false}` (three fields of the rendered config quoted): the whole config, B's values, and A's own reader never fired again. The flip is visible: A's 200-column diff went from split to unified. It was **unreachable in the single-reader composed install** (every reader was the same `() => loadDiffConfig()` over the same file, so the shared slot always held an equivalent value — which is exactly what the old allow-list reason claimed) and **real in a mixed install** (a standalone diff registers `() => DEFAULT_DIFF_CONFIG`, a different value) or in an in-process child session of the class this doc already names above. That gap between "cannot be observed here" and "cannot happen" is the whole reason shape-parity was worth doing rather than leaving allow-listed: config and theme are threaded per registration now (`registerDiffTools` hands its reader to the tool installers; `hlBlock(code, language, theme)`, `shouldUseSplit(diff, tw, cfg, maxRows?)` and `DiffComponent`'s constructor take them as values), and `packages/diff/src/config-threading.test.ts` pins the two-session case by driving installed renderers — a test against the leaf functions could not observe a shared holder.
